# 拼汪 PAWZZLE：关卡设计与开发交接文档

面向：后续接手本项目、负责新增关卡或更换美术的 AI 开发者。

基线：2026-10-25 的工作区实现。后续开发时应重新核对源码，本文中的“现有”不代表功能永远不变。

**你的交付物是可游玩的完整关卡：包含分区几何、正式图片、完整预览、运行数据、接入代码和验证记录。图片制作属于你的开发职责。你必须自行准备可用的文生图／参考图编辑能力，或自行编写达到交付质量的 SVG 插画；不能把寻找接口、配置脚本、绘制素材的工作转交给用户，也不能只留下提示词或占位图。**

本文描述开发流程，不代表仓库已经提供通用关卡编辑器或生图客户端。下文标为“建议新增”的文件、字段和接口，需要由接手 AI 实现。图片服务准备好以前，可以持续推进几何、SVG、数据接入和验证。

## 1. 接手后先做什么

1. 阅读 [README](../README.md)、[素材说明](ASSETS.md)、[验证记录](VERIFICATION.md)，查看 `git status --short`，保留工作区已有改动。
2. 阅读 [关卡注册](../src/level.js)、[拼图引擎](../src/puzzle-engine.js)、[界面与渲染](../src/main.js)，理解坐标、吸附和存档契约。
3. 查看第二、三关的完整预览与拼片总览，建立视觉标准；历史“彩底小贴纸版”不是第三关当前的参考标准。
4. 写一页关卡简报：主题、片数、难度、外轮廓、构图模式、美术风格、素材路线、存档兼容策略。
5. 自行选择并验证素材能力。已有授权的生图工具或接口可用就接通；不可用就采用 SVG 路线。先完成代表性样片，再批量制作。
6. 按“几何 → 图片 → 裁切／装配 → 接入 → 验证”的顺序完成，不以某一步产物代替整关交付。

若用户没有给出细节，沿用狗狗主题、600 × 600 逻辑画布、无需旋转的操作方式，选取 8–30 块内的合适难度，并在简报里记录设计决定。用户本次明确提出的主题或要求优先。

### 2.2 实现约束

| 事项 | 现有实现 | 新关卡的处理方式 |
| --- | --- | --- |
| 运行环境 | 原生 JavaScript、SVG、Node.js 20+；游戏无第三方运行依赖 | 图片在开发阶段生成，运行和构建不调用图片 API |
| 逻辑画布 | 现有三关均为 600 × 600 | 默认保持；改尺寸时同时调整桌面、移动端和排列验证 |
| 拼片操作 | 只平移；同组共享平移量；归位后锁定 | 不设计必须旋转、翻面或改变缩放才能完成的关卡 |
| 坐标 | `piece.path`、`bounds`、`center` 都在整关坐标系 | 不把单块路径归零后直接交给现有引擎 |
| 吸附 | 模型默认 18，界面传入 20，单位为画布单位 | 优先通过几何与图像设计调难度；当前没有每关吸附阈值配置 |
| 关卡选择 | `?level=01/02/03`；无有效参数时取 `LEVELS` 最后一项 | 追加新关会自动成为默认关，必须明确并验证这个结果 |
| 难度显示 | 文案由关卡提供；难度圆点按 `TOTAL >= 30` 切换 | 若新难度规则不同，需要改界面逻辑，单改文案不够 |
| 发布方式 | 构建复制 `index.html`、`src/`、`public/assets/` | 所有正式资源必须落盘；临时远程 URL 不能作为发布资源 |
| 开发服务 | `server.mjs` 对运行时模块使用明确白名单 | 新增的运行时模块及其依赖均需登记，否则开发时会 404 |

**平移量示例：**一块拼片的 `bounds.x = 120`，要让它的左边出现在桌面 `x = 800`，引擎的 `x` 应为 `680`。归位时每块的平移量都等于 `BOARD`，当前为 `{ x: 45, y: 60 }`，不再额外加各块的 `bounds`。

## 3. 如何设计一个有趣的关卡

### 3.1 先写简报，再画切线

建议新增 `docs/levels/<编号>-<主题>/brief.md`，至少回答：

| 项目 | 要写清楚的内容 |
| --- | --- |
| 主题 | 玩家最后拼出什么；这一关与已有关卡有何可见区别 |
| 体验 | 安静观察、轻松辨认、材质对照或密集拼接等具体体验 |
| 结构 | 片数、逻辑尺寸、外轮廓、轮廓拟形或自由曲线分区 |
| 视觉线索 | 主要依靠形状、毛色、五官、纹理或跨片连续画面 |
| 构图模式 | 一片一个完整主题形象，还是脸／身体／爪子的满版局部 |
| 风格 | 单一媒介、同系列变体，或明确配比的混合媒介 |
| 图片路线 | 参考图编辑、独立文生图、SVG，或事先规划的混合路线 |
| 兼容性 | 新关卡的 `id`、编号、`saveKey`；旧关改图是否保持几何 |
| 验收 | 样片、总览、桌面／手机操作、存档和通关检查 |

建议的难度分层如下。它是设计起点，不是已验证的完成时长承诺。

| 难度 | 建议片数 | 形状与图像安排 |
| --- | --- | --- |
| 入门 | 8–12 | 区域宽大；脸或主要特征完整；色块与形状差别明显；外沿容易辨认 |
| 标准 | 13–20 | 大小与朝向有变化；适量相似毛色；保留几个一眼能辨认的锚点 |
| 进阶 | 21–30 | 混合脸、身体和局部；靠纹理、轮廓共同判断；相似区域仍有可解释的区别 |

不要用细长碎片、难以拿起的小尖角、大片重复纯色或被裁坏的脸提高难度。超过 30 块属于新的容量范围，需要同步评估排列、移动端可操作性、加载和测试限制。

### 3.2 安排“先找到哪块，再拼哪块”

- 至少设计几个显著锚点，例如蓝眼睛、黑白斑点、大爪垫、明显侧脸，分别放在不同区域。
- 在蓝图上检查相邻块：如果毛色接近，让姿态、明暗、媒介或纹理方向至少有一项明显不同。
- 同一只正面狗脸改颜色不算一套独立素材。改变品种、视角、表情、身体部位和笔触结构。
- 入门关优先保全双眼、鼻子与嘴；局部特写关可以只画一只眼或一只爪，但简报和该片构图必须明确这是有意的局部。
- 默认采用独立拼片插画；若设计跨片连续场景，应从同一张主画面裁切，或严格共享跨边坐标。不要指望多次独立生图恰好接上同一条线。
- 总览中检查明暗节奏，避免全关都挤在同一种棕色、同一个正面视角。深色区域也必须在游戏缩放下可辨。

### 3.3 一个可执行的创意起点

例如新增“毛茸茸博物馆”：18 块，狗头外轮廓，标准难度；6 张彩铅、6 张版画、6 张剪纸，包含脸部、侧脸、蜷卧身体和爪子。为相邻区域交错安排媒介与毛色，选 3 块分别试做正脸、深色卷毛和窄边爪子。

这只是设计示例，尚未在代码中实现。使用 SVG 时，可将三种媒介设计为彩铅排线、木刻线纹和剪纸色面；不要把 SVG 模拟的效果标注为真实照片。

## 4. 几何先于图片

### 4.1 选择几何路线

- **犬形拼片**：参考 [contour-geometry.js](../src/contour-geometry.js)。先画顶点与共享曲线，让一侧的下巴自然成为另一侧的耳部凹口。宽阔区域优先，避免为了完整狗形产生细长尾巴和孤立小岛。
- **自由曲线拼片**：参考 [party-geometry.js](../src/party-geometry.js)。先布置错落种子、划分区域，再对共享边做适度弯曲，得到不同宽高与邻接关系。
- 不要把某关的生成算法视为任意轮廓都适用。第三关使用当前外轮廓的采样多边形；换成深凹或带孔轮廓时，应先确认分区算法不会生成断开的区域。

修改现有关卡几何前必须先定版本策略；新增关卡优先新增独立模块，避免改动旧关公用外轮廓时连带改变旧存档。

### 4.2 必须保持的不变量

1. **共享边只定义一次。**每条内部边恰好有两个所属拼片，分别正向和反向引用；外边只有一个所属拼片。反转三次贝塞尔曲线时，要交换控制点及起终点，多段曲线还要反转段顺序。
2. **共同顶点必须完全一致。**不要让相邻块分别计算并四舍五入各自的边界。采样点也应共享后反向使用。
3. **每块是一个连通、无自交、闭合的区域。**拼片并集覆盖目标外轮廓，内部不重叠、不留洞；相邻图整体连通。
4. **邻接关系来自共享边。**只有角点相接不算可吸附邻居。保持双向、去重、无自身引用。
5. **边界框包住真实曲线。**从最终曲线求极值或充分采样后向外取整，不能只按顶点取框。`center` 要处于合理的块内位置；凹多边形的面积中心可能落在外面，需要校验。
6. **所有消费者共享一套几何。**底板、交互命中、图片蒙版、独立拼片、完整预览不能各画一份近似切线。
7. **几何必须可复现。**生成算法使用固定种子或固定输入；页面加载时不能随机改变形状。散片初始排列可以随机。

第三关目前使用面积大于 5000、边界框长宽比小于 1.8 等专用检查，数值基于它的 600 × 600／30 块设计。新关卡需要按片数与触控体验设定指标，不能把这些数值当成所有关卡的通用定律。

新切线优先沿用 `M`、`C`、`Z` 等已使用的路径命令。通用关卡测试的采样器目前支持 `M/L/H/V/Q/C/Z` 及对应相对命令；如果几何使用 `A/S/T`，需要扩展或替换采样器，不能直接复制现有测试后宣称覆盖完整。插画内部路径与拼片切线路径应分开处理。

### 4.3 几何阶段要交出的检查图

先输出带拼片编号的外轮廓蓝图、邻接信息和单片轮廓参考。此时就验证：

- 密集采样下内部点恰被一块覆盖，外部点不被覆盖；拼片面积之和与外轮廓面积一致。
- 实际曲线而不是仅缓存的 `points` 能通过检查；边缘抗锯齿允许的误差与真正孔洞区分处理。
- 所有原尺寸拼片都能排进桌面和手机散片区，保持现有 14 画布单位间距，不旋转、不缩放、不遗漏。
- 代表性窄块仍能放下可辨识的内容。放不下时先修几何，再开始昂贵的素材制作。

现有 `artBounds` 是早期完整角色摆放所用的内部安全矩形。第三关满版流程已经不靠它缩小图片；新图可以把五官放在安全区域，但毛发、躯干和纹理仍应延伸到切边。

## 5. 如何制作不同风格的图片

### 5.1 先建立逐片美术表

参考现有第三关方向表，为每块记录主体、媒介、视角、构图、主色、识别特征和裁切重点。先排完整张表，再生成，避免最后几张随意重复。

下面的对象展示可供新流程采用的记录格式。`palette`、`focalPoint`、`mustKeep` 是建议新增的策划字段，现有第三关脚本不会读取它们；如需自动约束，要自行实现映射。

```json
{
  "id": "p01",
  "name": "回头的黑白边牧",
  "style": "木刻版画",
  "category": "fine-art",
  "medium": "limited-palette woodcut with directional carved fur lines",
  "subject": "A border collie turning over its broad shoulder; head and fur fill the frame.",
  "framing": "侧脸半身",
  "palette": ["#22201d", "#e6c894", "#9c5d3c"],
  "focalPoint": [0.52, 0.42],
  "mustKeep": ["可见眼睛", "鼻尖"],
  "cropAnchor": [0.5, 0.5],
  "cropZoom": 1
}
```

`cropAnchor` 为源图宽高的归一化坐标；现有裁切脚本以它为期望中心，并将裁框限制在图内。`cropZoom >= 1`；放大裁切只能更紧，不能用小于 1 的值缩成贴纸。`focalPoint` 应描述主体重点，与实际裁框中心不是同一个概念。

### 5.2 风格要改变绘制语言

| 风格 | 文生图中要描述的具体特征 | SVG 实现方向 |
| --- | --- | --- |
| 自然／胶片摄影 | 真实毛发、解剖结构、自然光；胶片版增加适量颗粒与暖色响应；近景填满画面 | 不承诺照片级效果；可换成明确命名的矢量写实插画 |
| 写实水彩 | 透明色层、颜料扩散、纸纹、边缘深浅变化；保持真实五官 | 多层低透明度色面、少量轮廓偏移、受控纹理；纸感不等于四周留白 |
| 油画／厚涂 | 可辨认的笔触、颜料厚度、明暗色块、毛流方向 | 定向短曲线与叠色块表现笔触，避免堆叠巨大滤镜 |
| 彩铅／炭笔 | 排线、交叉线、颗粒、线条疏密塑造体积 | 成组短线、不同线宽与透明度；在脸部结构上组织排线 |
| 水墨 | 墨色浓淡、干湿笔、毛边和少量暖色；主体仍充满区域 | 曲线路径、半透明墨块与局部枯笔纹理；不以空白替代内容 |
| 木刻／版画 | 几种限制色、阴阳线条、方向明确的刻痕 | 受裁切约束的线纹／图案，沿脸部和毛发方向排列 |
| 波普／漫画 | 粗细明确的轮廓、夸张表情、网点、清晰明暗分区 | 原生 path、pattern、有限色板；五官与姿态逐片变化 |
| 像素艺术 | 稳定像素格、有限色板、阶梯边缘、明确高光 | 同一网格上的 rect；主体保持像素感，外部拼片切线仍遵循统一几何 |
| 剪纸 | 叠层色面、可见纸纤维、少量层间阴影 | 多层闭合 path、少量局部阴影；主角放大到覆盖切边 |
| 黏土／软陶 | 圆润体积、轻微压痕、柔和接触阴影、手工材质 | 用渐变与有限高光做“黏土感矢量插画”，不冒充实拍 |

统一一关的色温、对比度与细节密度，同时让不同媒介保留明显差异。只给同一张图套不同色相滤镜，不能算“不同风格”。单一风格关也要有不同姿态和局部构图。

### 5.3 两种构图模式

**轮廓拟形模式（参考第二关）：**先给模型固定轮廓参考，让耳朵、面颊对应轮廓凸起，五官落在宽阔区域。保持参考画布、朝向、位置和比例，毛发覆盖整个有效区域并适当出血。最终轮廓仍由本地蒙版决定，不能直接采用模型返回的透明边界。

**满版局部模式（参考第三关）：**狗脸、躯干、爪子或毛发构成整个画面表面，四角仍是主体内容。源图不透明；不留白、不加彩色衬底、不把完整小狗缩小放在中间。五官／爪垫优先留在实际可见的内部区域，身体与毛发允许越过画面边界。

完整脸与局部特写不能混用验收标准。标为完整脸的拼片如果被切掉鼻子，应调整构图；标为眼睛局部的拼片则应判断眼睛是否清晰、周围纹理是否充足。

## 6. 文生图接口：接手 AI 必须自行准备

### 6.1 选择能力并验证

按实际环境选择最短可行路线：

1. **已提供的图片生成工具**：若当前 AI 环境提供可用的生图／编辑工具，按其说明直接生成并保存正式源文件。
2. **已有授权的服务、CLI 或技能**：核对本机已配置能力，使用现有授权完成调用。本项目第二关曾使用 `site-imagegen`，但这不代表新环境必然安装该技能，也不代表历史模型名仍然有效。
3. **自行编写服务适配器**：已有可用服务和凭据时，查阅该服务当前官方文档，确认鉴权、模型、请求字段、图片尺寸、编辑能力、响应格式，再做最小调用。
4. **没有可用服务或调用持续失败**：直接进入第 7 节的 SVG 路线，完成正式素材。不要以“请用户提供生图接口／API Key”作为默认交付结果，也不要凭空宣称调用成功。

“自行准备”是接通现有授权能力、实现必要脚本并完成验证，不是捏造接口地址、凭据或模型，也不意味着代替用户注册付费账号。用户若明确指定必须使用某个服务或照片级结果，无法满足时应报告该具体限制，不能把矢量插画冒充已满足的结果。一般关卡任务允许 SVG 时，应自主完成可行方案。

### 6.2 新适配器应具备的最小能力

建议将新客户端放在 `scripts/`，由开发者在命令行使用。以下是**待实现的接口约定**，不是仓库已有命令，也不是某家服务的 HTTP 参数：

```js
await generateAsset({
  levelId: 'dog-museum-v1',
  pieceId: 'p01',
  promptFile: 'docs/levels/04-museum/prompts/p01.txt',
  referenceFile: null, // 轮廓参考编辑时填写本地文件；服务必须支持编辑
  outputFile: 'work/museum-v1/source/p01.png',
  opaque: true,
});
// 建议返回：实际文件路径、真实宽高、内容哈希、请求记录位置。
```

实现要求：

- 将文字生成、参考图编辑能力分开检测；不要把只支持文生图的服务当作可精确编辑轮廓的服务。后者可改用满版源图加本地裁切。
- 通过现有工具的凭据管理或仅服务端／命令行可读的环境变量读取密钥，不放入 `src/`、`public/assets/`、提示词、manifest 或日志。
- 若新增自有适配器，可约定 `PAWZZLE_IMAGE_BASE_URL`、`PAWZZLE_IMAGE_MODEL`、`PAWZZLE_IMAGE_API_KEY`；这些不是现有项目变量。只提交无密钥的配置示例。若使用 `.env`，先添加对应忽略规则并明确如何加载，当前 `.gitignore` 没有替你忽略 `.env`。
- 不在前端接入生成服务，也不要求玩家提供密钥。静态资源准备完成后，启动、构建与游玩都应能离线于该服务运行。
- 正确处理服务实际返回的二进制、base64、下载地址或异步任务结果；校验 MIME、文件可解码性、真实尺寸与透明度。保存图片本体，不能只保存临时下载地址。
- 设置请求超时、有限次数的重试与并发上限；成功结果落盘后跳过重复调用。先试做约 3 张代表样片，再确定批量参数，避免未检查就批量重做。
- 提示词、参考图或参数变更时重新标识该片的输入版本；只重做失败或需要修正的片。服务若不支持 seed，不虚构可重复生成的保证。
- 将临时输出与正式资源分开；素材不齐或验收未通过时，不发布一半的新运行映射。

## 7. 没有接口时，自己使用 SVG 绘图

### 7.1 SVG 是可交付路线

现有渲染通过 `<image href="...">` 加载拼片，开发服务器也支持 `.svg`，因此新关卡可以直接使用独立 SVG 文件。**不必为了交付 SVG 先接通图片 API，也不必把 SVG 强制转成 PNG 才能运行。**

SVG 仍需达到正式插画质量：有清晰主体、独立姿态、面部结构、毛色分区和适合该风格的纹理。不能用同一个狗头改填充色重复 N 次，也不能用几个几何图形或文字编号充当最终素材。

制作顺序：

1. 为各片建立主体草图和配色，用大面积身体／毛发色面覆盖整个区域。
2. 根据实际可见区域布置脸、侧脸或爪子；核心特征留在有效内部，边缘用毛流和色块延续。
3. 分层画主体、毛色分区、眼鼻口、局部阴影、高光和媒介纹理；不同姿态使用不同路径。
4. 用统一风格参数控制线宽、色数与纹理密度；程序化纹理使用固定 seed。
5. 将整幅局部插画按固定 `piece.path` 裁切，输出独立 SVG，并用同一插画内容组装总图。

### 7.2 坐标与装配骨架

推荐在整关坐标系中画图。每张独立 SVG 的 `viewBox` 为该片的边界框，宽高比与 `bounds` 一致；界面会把它放回同一边界框。

以下代码只演示几何装配。`drawArtwork(piece)` 必须由你实现为正式插画生成函数，返回使用整关坐标的 SVG 内容；不能原样留下未实现函数作为交付。

```js
// 文件名和内部 ID 使用程序生成的字母、数字、短横线，保证唯一。
function makeSvgAssets(geometry, drawArtwork, prefix) {
  const wrap = (viewBox, width, height, body) =>
    `<svg xmlns="http://www.w3.org/2000/svg" viewBox="${viewBox}" ` +
    `width="${width}" height="${height}">${body}</svg>`;

  const entries = geometry.pieces.map(piece => {
    const b = piece.bounds;
    const id = `${prefix}-${piece.id}`;
    // 插画中的 gradient、pattern、filter 等 ID 也使用 id 作为前缀。
    const art = drawArtwork(piece, id);
    const body = `<defs><clipPath id="${id}-cut" clipPathUnits="userSpaceOnUse">` +
      `<path d="${piece.path}"/></clipPath></defs>` +
      `<g clip-path="url(#${id}-cut)">${art}</g>`;
    return {
      id: piece.id,
      body,
      svg: wrap(`${b.x} ${b.y} ${b.width} ${b.height}`, b.width, b.height, body),
    };
  });

  const outlineId = `${prefix}-outline`;
  const previewBody = `<defs><clipPath id="${outlineId}" clipPathUnits="userSpaceOnUse">` +
    `<path d="${geometry.outline}"/></clipPath></defs>` +
    `<g clip-path="url(#${outlineId})">${entries.map(e => e.body).join('')}</g>`;
  return {
    pieces: entries.map(({ id, svg }) => ({ id, svg })),
    preview: wrap(`0 0 ${geometry.width} ${geometry.height}`,
      geometry.width, geometry.height, previewBody),
  };
}
```

此骨架复用相同插画和裁切路径，但 SVG 渲染器仍可能在相邻独立 clip 的抗锯齿边缘显示细缝，不能仅凭字符串一致就判定视觉无缝。应在浏览器检查预览和完成态；必要时将 SVG 源图栅格化后，采用第 8 节的覆盖权重合成办法输出预览，并核对内部像素一致性。

其他约束：

- 文件自包含，不依赖远程字体、外链图片、脚本或 `foreignObject`。避免文本排版差异；需要编号时将其放在检查图中，不写进正式插画。
- 渐变、纹理和滤镜的 ID 必须按关卡与拼片加前缀，防止合成预览时冲突。
- 避免数万条不必要路径和大量全尺寸模糊滤镜；小屏下看不见的细节不值得拖慢拖动。
- 新 SVG 关不能直接交给现有 PNG 专用解析器。可验证 `viewBox`、路径与资源自包含性，并用实际浏览器或已安装的 SVG 栅格化工具检查像素、透明度与接缝。
- 如需栅格化，保留 SVG 源文件和导出命令；像素艺术不要经过模糊缩放破坏网格。

## 8. 裁切、透明度与完整预览

### 8.1 现有可用命令

以下命令已经存在，但分别绑定第二、三关的路径和输出，**不是传一个新关卡 ID 就能复用的通用命令**。新增关卡应新建脚本或先完成参数化，避免误覆盖旧素材。

```sh

npm run generate:contour -- --prepare

# 第二关：源图齐全后，裁切并生成运行映射。
npm run generate:contour

# 第三关：只输出已有源图的本地试切结果，不发布运行映射。
npm run generate:party -- --partial

# 第三关：完整素材的正式裁切与装配。
npm run generate:party
```

本地 Python 处理需要 Pillow、NumPy。优先使用已有解释器，可用 `PAWZZLE_PYTHON=/path/to/python` 指定；不要为了读取已生成资源给游戏增加 Python 运行依赖。

关键实现：[第三关入口](../scripts/generate-party-level.mjs)、[满版裁切](../scripts/prepare-party-art.py)、[第二关入口](../scripts/generate-contour-level.mjs)、[轮廓参考与裁切](../scripts/prepare-contour-art.py)。

### 8.2 满版图片裁切算法

设边界框宽高为 `bw, bh`，像素倍率为 `s`，实际源图尺寸为 `sw, sh`：

```text
输出宽高：W = bw × s，H = bh × s
等比覆盖倍率：k = max(W / sw, H / sh)
源图裁框宽高：cw = W / k / cropZoom，ch = H / k / cropZoom
按 cropAnchor 计算裁框中心，并把裁框限制在源图范围内
将裁框缩放为 W × H，再施加固定的异形蒙版
```

运行图片的宽高比必须与 `bounds` 一致，避免 `<image>` 默认保持比例时产生留白。不能按肉眼可见内容自动裁边、居中或挪动角色；轮廓参考路线尤其需要保留原来的画布映射。

当前第二、三关 PNG 使用 `pixelScale: 3`，所以 600 × 600 的完整预览为 1800 × 1800。服务返回尺寸可能与请求尺寸不同，始终读取真实宽高。检查源图在有效裁框内是否有足够分辨率，放大不能补回不存在的细节。

### 8.3 两种透明度不能混淆

| 产物 | 正确要求 |
| --- | --- |
| 第三关式满版源图 | 全图不透明，主体内容延伸到边缘；透明角色抠图不符合此流程 |
| 最终独立 PNG／SVG 拼片 | 轮廓内被插画填满，轮廓外透明，边缘允许正常抗锯齿 |
| 完整预览 | 外轮廓外透明，内部无透明孔洞，与可玩拼片使用相同内容及坐标 |

不要依赖 `piece.fill` 底色遮住图片内部缺失。底色可以保留作渲染底层，但不能成为围绕小角色的一圈彩色底板。

### 8.4 预览必须由可玩素材合成

不能另外生成一张“差不多”的漂亮原图。预览与实际拼片的脸、姿态、纹理和裁切位置必须一致。

相邻抗锯齿边若直接按普通透明叠加，会出现偏淡细缝。现有 PNG 合成先累计 `颜色 × 覆盖权重` 与权重总和，再归一化颜色，最后应用统一外轮廓的透明蒙版。复用或扩展此逻辑时，要同时验证内部不透明、外部透明、非边缘内部像素一致。

不要通过放大路径、增加粗描边、随机覆盖色块掩盖真实几何缝隙。修复顺序应为：共享几何 → 采样／蒙版 → 合成与抗锯齿。

新生成脚本宜先写入 `work/<关卡>/`，全部检查通过后再发布正式资源和数据。现有第三关 `--partial` 可用于试切，但不要将现有完整模式理解为具备所有文件的原子回滚保证。

### 9.4 存档版本的关键陷阱

当前引擎的存档签名包含 **`puzzleId`、拼片 ID 与邻接关系**，不包含路径、边界框、画布尺寸或图片。仅改曲线而保留旧 ID 与邻接，旧存档仍可能被接受。

| 改动 | 处理策略 |
| --- | --- |
| 同一几何，只换图片／风格 | 保留关卡 `id`、拼片 ID、`saveKey`；更新 `artRevision` 和版本化图片路径；验证进度可恢复 |
| 改轮廓、曲线、尺寸、片数、拼片 ID 或邻接 | 升级关卡数据 `id` 与注册处 `saveKey`，或实现并验证明确迁移；不能只修改几何模块自身的 ID |
| 完全新增关卡 | 使用新的关卡 ID、编号和存档键，保留旧关独立进度 |

不要通过清空所有 `localStorage` 解决版本问题。也不要认为设置 `artRevision` 就会自动刷新图片缓存；生产资源应使用版本化路径或文件名。

## 10. 验收与完成标准

### 10.1 每次先看样片

批量前选择约 3 个有代表性的区域：普通中央块、外沿／窄边块、深色或细节复杂块。看源图，也看实际裁切图，再放进游戏缩放下检查。源图漂亮但裁后失去主体，仍然不合格。

正式出齐后查看全关总览，逐片记录通过／需重做：

- 主体可辨，构图与美术表一致；完整五官和有意局部各按约定检查。
- 风格差异真实可见，姿态和纹理不重复，相邻区域有足够辨认线索。
- 内容延伸至切边，无白边、透明孔洞、彩底小贴纸、说明文字、参考线或水印。
- 预览与拼片一致；没有为追求好看重新生成另一张参考原图。
- 在实际小屏缩放下仍可辨认、拿取和移动；仅查看高分辨率总览不算完成验证。

像素统计能发现纯色占位或透明洞，但不能证明画面审美合格。不要靠添加噪点使空白图片通过细节阈值，也不要为容纳坏图而随意调低现有检查标准。

### 10.2 自动验证

```sh
npm test
npm run build
npm run dev
```

新增关卡至少验证：

| 类别 | 检查内容 |
| --- | --- |
| 几何 | 路径有限且闭合、无自交与孤岛；共享边反向复用；覆盖无孔洞／重叠；相邻图连通 |
| 数据 | ID 与图片路径有效；名称齐全；边界框包含实际曲线；图片尺寸／viewBox 正确 |
| 图像 | 透明度正确、主体有内容、边缘铺满、预览内部像素与拼片一致；SVG 用适合的渲染检查 |
| 排列 | 桌面和手机散片区容纳全部实际边界框；多种输入顺序下不丢片、不重叠 |
| 模型 | 场外拼接、整组移动、归位锁定、帮助通关、重开和恢复 |
| 兼容 | 旧关继续可玩；跨关存档拒绝；改图兼容或几何升级策略符合设计 |
| 发布 | 开发服务与构建产物中的新模块、图片、预览均能加载；无生成服务依赖 |

不要照抄历史文档的“多少项通过”作为本次结果。记录实际运行命令、通过情况和未验证项。新增关卡时应写能抓住真实错误的检查；仅复制实现或只断言文件存在不够。

### 10.3 浏览器操作

至少在一个桌面视口和一个手机宽度视口完成：

1. 从关卡选择器与 `/?level=<编号>` 进入，确认标题、片数、所有图片和完整预览正确。
2. 把真实相邻的两片在底板外拼成一组，移动整组，再吸附到底板，确认组内相对位置和进度正确。
3. 检查暂停、原图预览、整理、帮助、键盘操作；帮助以拼片组为单位，不一定每次只增加 1。
4. 刷新并切换旧关，验证进度独立且可恢复；完成新关后检查成功弹窗和重开。
5. 手机宽度下所有拼片可达，无意外横向溢出；拖动拼片与空白处滚动互不妨碍。
6. 查看控制台与失败请求，确认新增模块没有被服务器白名单遗漏。

手机模拟视口、模拟触摸和真实 iOS／Android 硬件测试应分别记录，不互相冒充。保存至少一张散片状态和一张完整预览／完成态截图。
